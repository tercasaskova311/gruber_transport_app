# Gruber Logistics Hackaton Challenge 2026 — Logistics Grand Prix

## 1. The challenge

You are the dispatcher of a European trucking company.

You get a scenario: a set of **cities**, a fleet of **trucks** and a list of transport **orders**. Your job is to build a **plan** that tells every truck which orders to pick up and deliver, and in which order.

A good plan:

- delivers as many orders as possible,
- keeps cost low,
- avoids driving empty,
- emits as little CO₂ as possible,
- breaks no rules.

The API simulates your plan and returns a **score** (max **1000**). The highest score wins.

You can use any language, any algorithm (greedy, heuristics, metaheuristics, MIP solvers, ML…) and any tooling. Only the submitted plan counts.

---

## 2. How it works

1. Pick a scenario: `GET /Hackaton2026/Scenarios`.
2. Download its data: cities, trucks, orders and the distance matrix.
3. Build a plan with your algorithm.
4. Check the plan: `POST /Hackaton2026/Submissions/{scenarioId}/Validate`.
5. Inspect the metrics: `POST /Hackaton2026/Submissions/{scenarioId}/Simulate`.
6. Get the score: `POST /Hackaton2026/Submissions/{scenarioId}/Score`.
7. Improve and repeat.

Scenario data is generated with random cities, trucks and orders **when the application starts**. While the application runs, every team gets exactly the same data; after a restart all scenarios are regenerated (new cities), so always fetch fresh data before planning.

Swagger UI is available at `/swagger`.

## 4. Domain model

### 4.1 City

All cities are real European cities. City IDs are global and stable, so `C001` is always the same city in every scenario.

```json
{
  "id": "C001",
  "name": "Belgrade",
  "country": "RS",
  "latitude": 44.79,
  "longitude": 20.45
}
```

### 4.2 Truck

```json
{
  "id": "T01",
  "start_city": "C001",
  "capacity_kg": 12000,
  "type": "standard",
  "cost_per_km": 1.2,
  "co2_per_km": 0.85
}
```

| Field | Meaning |
|---|---|
| `start_city` | Where the truck is when the plan starts |
| `capacity_kg` | Maximum load the truck can carry at any moment |
| `type` | `standard`, `refrigerated` or `hazmat` |
| `cost_per_km` | Cost (€) for every km driven, loaded or empty |
| `co2_per_km` | CO₂ (kg) for every km driven, loaded or empty |

### 4.3 Order

```json
{
  "id": "O001",
  "pickup_city": "C012",
  "delivery_city": "C045",
  "weight_kg": 3200,
  "required_truck_type": null
}
```

If `required_truck_type` is not `null`, only a truck of that type may carry the order.

### 4.4 Distance matrix

The matrix is symmetric, in kilometres, with `0` on the diagonal. It contains only the cities of the scenario.

The distances are approximate road distances: the great-circle distance between the two cities × 1.3.

It is available in two formats.

**JSON** — `GET /Hackaton2026/Scenarios/{id}/DistanceMatrix`

```json
{
  "C001": { "C001": 0,   "C002": 107, "C003": 287 },
  "C002": { "C001": 107, "C002": 0,   "C003": 335 },
  "C003": { "C001": 287, "C002": 335, "C003": 0   }
}
```

**CSV** — `GET /Hackaton2026/Scenarios/{id}/DistanceMatrix/csv`

```
city_id,C001,C002,C003
C001,0,107,287
C002,107,0,335
C003,287,335,0
```

## 6. Plan (submission) format

A plan is a JSON object:

- **key** = truck ID,
- **value** = ordered list of stops.

```json
{
  "T01": [
	{ "action": "pickup",   "order": "O003" },
	{ "action": "pickup",   "order": "O011" },
	{ "action": "delivery", "order": "O003" },
	{ "action": "delivery", "order": "O011" }
  ],
  "T02": [
	{ "action": "pickup",   "order": "O007" },
	{ "action": "delivery", "order": "O007" }
  ],
  "T03": []
}
```

**Rules of interpretation**

- `action` is `"pickup"` or `"delivery"`.
- The truck starts at its `start_city` and drives to the city of each stop, in list order:
  - `pickup` → the order's `pickup_city`
  - `delivery` → the order's `delivery_city`
- Consecutive stops in the same city cost 0 km.
- Trucks **do not** return to their start city at the end.
- A truck may carry several orders at once (consolidation), as long as capacity is never exceeded.
- Unused trucks can be omitted or given an empty list.
- Orders that are not in the plan are simply not fulfilled. There is no extra penalty, but you lose fulfillment points.

## 7. Validation rules

Every violation costs **20 points**.

| Rule code | Description |
|---|---|
| `unknown_truck` | Truck ID does not exist in the scenario |
| `unknown_order` | Order ID does not exist in the scenario |
| `unknown_action` | `action` is not `pickup` / `delivery` |
| `order_assigned_multiple_times` | Same order appears on more than one truck |
| `duplicate_pickup` | Order picked up twice |
| `duplicate_delivery` | Order delivered twice |
| `delivery_before_pickup` | Delivery stop appears before its pickup |
| `pickup_without_delivery` | Order picked up but never delivered |
| `capacity_exceeded` | A pickup would push the load above `capacity_kg`. The pickup is **rejected** |
| `truck_type_mismatch` | Order requires a truck type that the assigned truck does not have |

**How invalid stops are simulated**

- Stops that cannot be executed (unknown order or action, delivery before pickup, duplicates, an order already taken by another truck) are **skipped**.
- Orders delivered by a truck of the wrong type are **not counted** as fulfilled.
- A pickup that would exceed the truck's capacity is **rejected**: the order is not loaded, its later delivery stop is ignored, and the order is **not fulfilled**. The `capacity_exceeded` penalty is still applied.

## 8. Metrics

| Metric | Description |
|---|---|
| `total_km` | Total km driven by all trucks |
| `loaded_km` | Km driven with at least one order on board |
| `empty_km` | Km driven with nothing on board |
| `total_cost` | Σ (km × `cost_per_km`) per truck |
| `total_co2` | Σ (km × `co2_per_km`) per truck |
| `orders_fulfilled` | Orders correctly picked up and delivered |
| `orders_total` | Number of orders in the scenario |
| `truck_utilization` | Average load / capacity, weighted by km driven |

Per-truck metrics are also returned: route (list of city IDs), km, cost, CO₂, max load and utilization.

### 8.1 Time simulation and time windows

Time is **calculated**, not waited for in real time. Minute `0` = plan start (Day 1, 06:00); all trucks start at minute 0.

| Rule | Value |
|---|---|
| Average speed | 70 km/h (`driving_min = ceil(km * 60 / 70)`) |
| Service time per stop (pickup or delivery) | 30 min |
| Break | 45 min after 4.5 h of driving (inserted automatically) |
| Daily rest | 11 h after 9 h of driving (inserted automatically) |
| Waiting / service ≥ 45 min | counts as a break |

none in `scenario_small`, ~10% in `scenario_middle`, ~20% in `scenario_big`, ~30% in `scenario_competitive`

- **Early** arrival → the truck waits until `from`.
- **Late** arrival (up to 60 min after `to`) → order still fulfilled, but it keeps only part of its value: linearly from 100% (on time) down to **50% at 60 min late** (e.g. 30 min late = 75%). `late_penalty` in the score breakdown shows the points lost this way.
- More than 60 min late → order is **not fulfilled**.
- Every time window is generated so that the order is reachable on time when the nearest compatible truck serves it alone (driving time, breaks and service included). Combining it with other orders is your challenge.

The plan format does not change. Every truck in the simulation response contains `finish_min`, `driving_min`, `break_and_rest_min` and a `schedule` (arrival, wait, late and departure minute per stop). Global metrics include `orders_late`, `orders_too_late`, `total_late_min` and `penalized_late_min`.

## 9. Scoring

Each component is normalized to the range **0–100**:

| Component | Formula | Weight |
|---|---|---|
| Fulfillment | `100 × value_fulfilled / value_total` | **50%** |
| Cost efficiency | `100 × min(1, reference_cost / total_cost)` | **20%** |
| Loaded ratio | `100 × loaded_km / total_km` | **15%** |
| CO₂ efficiency | `100 × min(1, reference_co2 / total_co2)` | **15%** |

The reference values are calculated from the orders you fulfilled:

- `reference_km` = sum of the direct `pickup_city → delivery_city` distances of **all** orders × (`orders_fulfilled` / `orders_total`)
- `reference_cost` = `reference_km` × cheapest `cost_per_km` in the fleet
- `reference_co2` = `reference_km` × lowest `co2_per_km` in the fleet

The final score is:

```
score = 10 × (0.50·fulfillment + 0.20·cost_eff + 0.15·loaded_ratio + 0.15·co2_eff)
		− 20 × number_of_violations
```

Maximum score is **1000**. The score can be negative.

### 9.1 Order value

Orders are not worth the same. Every order has a `value` (returned in the order list):

| Order | Value |
|---|---|
| Normal | 1.0 |
| Refrigerated | 1.5 |
| Hazmat | 1.5 |
| Has a pickup or delivery time window | +0.5 |

Example: a hazmat order with a time window is worth 2.0 normal orders.

**Tips**

- Fulfillment is worth half the score, so first make sure every order is delivered.
- Consolidating orders (several pickups before deliveries) reduces km and empty km.
- Choose trucks that are cheap and clean for long routes.
- Avoid long empty repositioning drives.
- Always run `/Validate` first. One violation costs 20 points (2% of the maximum score).

## 12. FAQ

**Do trucks have time windows or driving-hour limits?**
Yes. Some orders have time windows and drivers take automatic breaks and daily rests. See section 8.1.

**Can a truck visit the same city multiple times?**
Yes.

**Can I split an order between trucks?**
No. An order is carried as a whole by one truck.

**Do I have to use all trucks?**
No. Unused trucks cost nothing.

**Is the data going to change?**
Scenarios are regenerated with new random data when the server restarts. While it runs, data is fixed and the same for all teams. Always load fresh data before planning.

**What happens if I lose my API key?**
Ask the organizers. Do not share your key with other teams: all attempts are recorded under your team.
